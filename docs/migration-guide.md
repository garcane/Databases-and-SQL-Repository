# Migration Guide — SQL Server to PostgreSQL

Every mapping below was applied to real code in this repository and executed on
PostgreSQL 18.4. Where a construct could not be ported, that is stated plainly
along with what replaced it.

---

## 1. Required dialect mappings

| SQL Server | PostgreSQL | Where applied |
|---|---|---|
| `IDENTITY(1,1)` | `GENERATED ALWAYS AS IDENTITY` (warehouse)<br/>`GENERATED BY DEFAULT AS IDENTITY` (staging, reference) | [`20_dimensions.sql`](../postgres/database/20_dimensions.sql), [`10_staging.sql`](../postgres/database/10_staging.sql) |
| `GETDATE()` | `CURRENT_TIMESTAMP` | [`00_schemas.sql`](../postgres/database/00_schemas.sql), all loaders |
| `ISNULL(x, y)` | `COALESCE(x, y)` | [`20_load_facts.sql`](../postgres/functions/20_load_facts.sql), [`40_reference_objects.sql`](../postgres/functions/40_reference_objects.sql) |
| `SELECT TOP 10` | `SELECT ... LIMIT 10` | tuning examples |
| `a + b` (string concat) | `a \|\| b` | [`10_load_dimensions.sql`](../postgres/functions/10_load_dimensions.sql), [`10_ported_views.sql`](../postgres/views/10_ported_views.sql) |
| `TRY / CATCH` | `BEGIN ... EXCEPTION WHEN ... THEN` | [`30_run_full_load.sql`](../postgres/functions/30_run_full_load.sql) |

### `ALWAYS` vs `BY DEFAULT` — not interchangeable

`GENERATED ALWAYS` rejects an explicit insert unless every statement carries
`OVERRIDING SYSTEM VALUE`. That is exactly what you want for warehouse surrogate
keys: nothing outside the ETL should invent one.

Staging is the opposite case — it is loaded with the source system's own key
values, so `BY DEFAULT` is correct there. The reference `course` table makes
this concrete: its IDs are Microsoft course codes (`20761`, `66378`), not
sequence values, and the source loads them inside `SET IDENTITY_INSERT ON/OFF`.

> **The trap.** Explicitly inserted values do **not** advance a PostgreSQL
> sequence. The next generated key would be `1`, colliding with loaded data and
> failing on the primary key. T-SQL reseeds automatically when
> `SET IDENTITY_INSERT` is switched off; PostgreSQL does not. Every seed script
> here ends with `setval()` — see [`00_load_staging.sql`](../postgres/seed/00_load_staging.sql).

### `TRY/CATCH` → `BEGIN ... EXCEPTION`: three differences that break loads

```sql
-- T-SQL
BEGIN TRY
    BEGIN TRANSACTION
    ...
    COMMIT TRANSACTION
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION
    INSERT INTO LoadAudit(...) VALUES (ERROR_MESSAGE(), ...)
    THROW
END CATCH
```

1. **A PL/pgSQL block with an `EXCEPTION` clause is already a subtransaction.**
   PostgreSQL sets a savepoint on entry and rolls back to it when the handler
   fires. There is no `@@TRANCOUNT` to test and no explicit `ROLLBACK` to issue —
   attempting one raises an error of its own.

2. **The audit row will vanish.** Because the handler rolls back everything the
   block did, an audit row written *inside* the handler is rolled back too when
   the error is re-raised. This is the single most common bug when porting this
   pattern: the audit trail disappears at exactly the moment it is needed. The
   fix used here is a `PROCEDURE` with explicit `COMMIT`, so the batch row is
   committed *before* the work starts and the failure record is committed
   independently.

3. **Bare `RAISE` re-raises with the original `SQLSTATE`.** Using
   `RAISE EXCEPTION '%', SQLERRM` instead discards it, turning a diagnosable
   `23505` unique violation into a generic `P0001`.

Verified: injecting bad source data produced a rolled-back load, a `FAILED`
batch row that **survived**, and the original `SQLSTATE 23514` re-raised.

## 2. Data type mappings

| SQL Server | PostgreSQL | Note |
|---|---|---|
| `nvarchar(n)` | `varchar(n)` | PostgreSQL is Unicode throughout; no `n` prefix needed |
| `nchar(n)` | `char(n)` | Blank-padding semantics preserved |
| `ntext`, `text` | `text` | No length limit, no deprecated LOB handling |
| `image`, `varbinary` | `bytea` | |
| `money` | `numeric(19,4)` | **Not** PostgreSQL's `money` — see below |
| `bit` | `boolean` | `0/1` casts on load |
| `real` | `real` → `numeric(5,4)` at the warehouse boundary | See below |
| `datetime` | `timestamp(3)` | Source carries no time zone |
| `datetime2`, `datetimeoffset` | `timestamp`, `timestamptz` | |
| `uniqueidentifier` | `uuid` | |
| `smallint`, `int`, `bigint` | identical | |

### Avoid PostgreSQL's `money`

It looks like a natural match and is a trap: `money` is locale-dependent. Its
output format changes with `lc_monetary`, and its behaviour under division and
aggregation is surprising. `numeric(19,4)` is exact, portable and predictable.

### Date literals: the defect that finds you months later

The source writes dates as US `M/D/YYYY` — `INSERT ... VALUES(10248, 'VINET', 5, '7/4/1996', ...)`.
Extracted verbatim into a CSV and loaded, the meaning of that value depends on
the **loading server's** `DateStyle`:

```sql
SET DateStyle='ISO,MDY';  SELECT '7/4/1996'::date;   -->  1996-07-04
SET DateStyle='ISO,DMY';  SELECT '7/4/1996'::date;   -->  1996-04-07
```

Both succeed. Neither warns. `DMY` is the default in most UK and European
locales, so a warehouse built there would place every order three months from
where it belongs — and **no constraint or test could detect it**, because every
loaded value is a perfectly valid date. It would surface as an inexplicable
quarterly revenue shift, long after the migration was signed off.

This was caught in this repository *after* the pipeline was already loading and
reconciling cleanly, because the test cluster happened to default to `MDY`. Real
reconciliation on revenue totals did not catch it either: shuffling dates within
the same dataset changes no sum.

**Fix applied at extraction**, not at load. `extract_northwind_data.py`
normalises every date column to ISO 8601, so the CSV means one thing everywhere,
independent of any server setting. Setting `DateStyle` in the load script would
also work but leaves the CSV ambiguous for anyone else who reads it.

Verified by building the entire warehouse on a database set to
`DateStyle='ISO,DMY'`: order 10248 loads as `1996-07-04` and the annual
distribution is unchanged at 1996=152, 1997=408, 1998=270.

This is the same class of defect as the source's `'2015/01/01'` literal in
`ResetBookStock`, noted below — ambiguous date formats are a migration hazard in
both directions.

### `real` discount → `numeric`

`Order Details.Discount` is `real`, a binary float: `0.15` is actually stored as
`0.150000005960464`. Left alone, that artefact propagates into every revenue
figure. The port rounds at the warehouse boundary:

```sql
ROUND(od.discount::numeric, 4)   -- real -> numeric(5,4)
```

Revenue reconciles to the penny afterwards: **£1,265,793.04** across staging,
warehouse and presentation.

## 3. Constructs that could NOT be ported

### `CHECK` constraints using non-immutable functions

The source declares:

```sql
CONSTRAINT CK_Birthdate CHECK (BirthDate < getdate())
```

PostgreSQL rejects this. `CURRENT_TIMESTAMP` is `STABLE`, not `IMMUTABLE`, and
`CHECK` expressions must be immutable.

This is not a PostgreSQL limitation so much as PostgreSQL refusing something
that was never sound: SQL Server evaluates the constraint only on write and
never re-verifies existing rows, so a row valid in 1998 is never re-checked. The
rule moved to [`tests/validation.sql`](../tests/validation.sql) as check
`BIZ-001`, where it is evaluated against **every** row on every run.

### `WITH CHECK OPTION` on a non-updatable view

The author's `Managers` view carries `WITH CHECK OPTION`, but the view contains
`DISTINCT` and a self-join, so it is not updatable in either dialect and the
option can never fire. PostgreSQL rejects it outright:

```
ERROR:  WITH CHECK OPTION is supported only on automatically updatable views
```

Omitted from the port. Behaviour is unchanged, because there was no behaviour to
preserve.

### Implicit `bit`-to-string coercion

The vendor view `Current Product List` filters `WHERE Discontinued = 'N'` —
comparing a `bit` column to a *string*. SQL Server coerces silently; PostgreSQL
does not:

```
ERROR:  invalid input syntax for type boolean: "N"
```

Ported as `WHERE NOT discontinued`.

### Clustered indexes

SQL Server's `PRIMARY KEY CLUSTERED` determines physical row order. PostgreSQL
has no maintained clustered index; `CLUSTER` is a one-off reorganisation that
degrades as rows are updated. The clause is simply dropped — PostgreSQL's heap
plus visibility-map-backed index-only scans cover the same ground differently.

## 4. Idiom upgrades

Constructs that port literally, but shouldn't.

### `MERGE` → `INSERT ... ON CONFLICT`

SQL Server's `MERGE` has a long history of concurrency bugs. `ON CONFLICT`
resolves against a *named* unique constraint atomically:

```sql
INSERT INTO warehouse.dim_shipper (...) VALUES (...)
ON CONFLICT ON CONSTRAINT uq_dim_shipper_natural DO UPDATE
   SET company_name = EXCLUDED.company_name, ...
 WHERE (dim_shipper.company_name, dim_shipper.phone)
       IS DISTINCT FROM (EXCLUDED.company_name, EXCLUDED.phone);
```

> The `WHERE` guard matters. Without it, every re-run rewrites every row —
> creating dead tuples for `VACUUM` to reclaim and destroying the audit value of
> `dw_updated_at`. Adding it turned a re-run of the fact loaders from
> "2,155 rows updated" into a genuine no-op.

### Variable-accumulator string building → `string_agg`

The source builds a delimited list by assigning to a variable inside a `SELECT`:

```sql
SELECT @CourseString = ISNULL(@CourseString + ', ' + C.CourseName, C.CourseName) FROM ...
```

This relies on per-row assignment order that Microsoft has **never guaranteed**;
it silently produces wrong results when the plan changes. PostgreSQL has a
first-class aggregate with deterministic ordering:

```sql
SELECT string_agg(c.course_name, ', ' ORDER BY c.course_name) FROM ...
```

### Recursive CTE / `WHILE` for calendars → `generate_series`

```sql
FROM generate_series(p_from_date::timestamp, p_to_date::timestamp, INTERVAL '1 day') AS d
```

### Hard-coded year views → grouped views

The source ships `Category Sales for 1997` and `Product Sales for 1997`, with
the year baked into the view body — so 1998 sales were invisible until someone
wrote another view. Replaced by `sales_by_category_year`, grouped rather than
filtered.

## 5. Capabilities gained

Not everything is a compromise. These have no SQL Server equivalent and are used
throughout.

| Feature | Used for |
|---|---|
| `EXCLUDE USING gist` | Making overlapping SCD2 versions **physically impossible**. SQL Server has no declarative equivalent; it relies on procedural discipline plus an audit query |
| Generated columns (`STORED`) | `is_current`, `validity`, `gross/discount/net_amount`, `days_to_ship` — arithmetic defined once, cannot drift between reports, cannot be left stale by a partial reload |
| Range types + `&&` | `tstzrange(valid_from, valid_to)` as a first-class value |
| Partial indexes | `WHERE is_current` — smaller index, and it doubles as the one-current-row constraint |
| `FILTER (WHERE ...)` | Conditional aggregates without nested `CASE` |
| Expression indexes | Indexing `EXTRACT(YEAR FROM ...)` without a persisted computed column |
| Transactional DDL | A failed migration rolls back completely |

## 6. Findings in the source implementation

Catalogued during the port. None were "fixed" in the golden source — it is
preserved byte for byte.

### Eight pairs of duplicate indexes

| Table | Column | Duplicate index names |
|---|---|---|
| Orders | CustomerID | `CustomerID`, `CustomersOrders` |
| Orders | EmployeeID | `EmployeeID`, `EmployeesOrders` |
| Orders | ShipVia | `ShippersOrders` (+ FK) |
| Products | CategoryID | `CategoryID`, `CategoriesProducts` |
| Products | SupplierID | `SupplierID`, `SuppliersProducts` |
| Order Details | OrderID | `OrderID`, `OrdersOrder_Details` |
| Order Details | ProductID | `ProductID`, `ProductsOrder_Details` |

Every duplicate costs write throughput on every insert and update, and can never
be chosen by the planner over its twin. Not carried forward; check `STR-006`
asserts the port did not inherit the habit.

### Other observations

- **`Order Subtotals`** computes
  `SUM(CONVERT(money, (UnitPrice*Quantity*(1-Discount)/100))*100)`. The
  `/100 ... *100` exists only to force `money` through an intermediate rounding
  step. `numeric` needs no such wart; the port expresses the arithmetic directly.
- **`Managers`** self-join reads backwards — the alias `m` holds the
  *subordinate*. Preserved verbatim in the port; the result set is identical.
- **Date literals** such as `'2015/01/01'` depend on the server's `DATEFORMAT`
  and can mean different days on differently configured instances. Written as
  unambiguous ISO dates in the port.
- **`udf_DelegateDays`** returns `NULL` for a delegate with no attendance, where
  `0` is meant. The port adds `COALESCE` — flagged, not silent.
- **`create_qastore.sql` is UTF-16LE**, not UTF-8. Preserved byte for byte and
  marked `binary` in `.gitattributes` to protect its BOM.
- **`northwind.sql` is cp1252.** Reading it as UTF-8 fails outright on
  `0xF3` ("Constitución"); reading with `errors="replace"` would silently corrupt
  657 bytes across customer and supplier addresses. The extractor decodes cp1252
  explicitly.
- **`N'...'` national-character prefixes** must be stripped during extraction.
  Treated as data, `N'VINET'` becomes the six-character string `NVINET` and
  overflows `char(5)` on load.

## 7. SSIS and orchestration

**There are no SSIS packages in this repository or its Git history** — no
`.dtsx`, `.dtproj` or `.ispac` files exist. Loading was performed by executing
T-SQL scripts directly. Nothing was removed; there was nothing to remove, and no
empty `sqlserver/ssis/` folder was created to imply otherwise.

For the PostgreSQL target, the equivalent responsibilities map as follows.

| SSIS concept | PostgreSQL-native equivalent |
|---|---|
| Data Flow Task (bulk load) | `COPY` / `\copy` — the mechanism every PG bulk loader ultimately calls |
| Control Flow, precedence constraints | `warehouse.run_full_load()` procedure |
| Event handlers, `OnError` | `BEGIN ... EXCEPTION`, with `etl.load_batch` as the audit sink |
| Slowly Changing Dimension wizard | Explicit PL/pgSQL loaders — auditable, diffable, testable |
| Package configuration | Function parameters |
| Logging | `etl.load_batch` + `RAISE NOTICE` |

### When to introduce a scheduler

Right now the pipeline is invoked by `psql`, which is the honest answer for
3,308 rows on a fixed extract. Reach for more only when a real requirement
appears:

- **Apache Airflow** — when you need scheduling, retries, backfills, SLAs, or
  cross-system dependencies. One DAG, one task per loader, dependencies already
  expressed by the load order.
- **dbt** — when transformation logic outgrows hand-written SQL and you want
  lineage graphs, generated docs and tests as first-class objects. The
  `staging → warehouse → presentation` split maps directly onto dbt's
  staging/intermediate/marts convention, and the checks in `tests/` become
  schema tests.
- **Python + psycopg2** — when extraction needs API calls, file watching or
  credential handling. Keep the transformation in SQL; use Python for the
  plumbing.

**What not to reach for.** Kafka, Spark and a distributed lakehouse are all
wrong for 3,308 rows. Adding them would demonstrate tool familiarity at the cost
of demonstrating judgement.

## 8. Migration strategy

The phased approach used here, and why.

| Phase | Step | Rationale |
|---|---|---|
| 1 | Analyse and map | Nothing modified. Found: no SSIS, no author procedures, four separate databases |
| 2 | Isolate the reference | `git mv` only, tagged `archive/ms-sql-reference`. 100% rename similarity, blobs byte-identical |
| 3 | DDL first | Schemas, types, constraints — verified by asserting violations are *rejected* |
| 4 | Logic and data | Loaders, views, seed pipeline. Reconciled to the penny |
| 5 | Tests | 71 checks, verified by deliberate breakage |
| 6 | Documentation | This guide |

### Principles worth stealing

1. **Preserve the source absolutely.** The reference implementation is tagged and
   pinned with `sqlserver/** -text` in `.gitattributes` so end-of-line
   normalisation can never rewrite it. 59 of 60 original blobs are byte-identical.
2. **Port faithfully, then improve deliberately — and say which is which.** Every
   deviation is commented at the object it affects.
3. **Verify behaviour, not syntax.** "It compiles" is not evidence. Assert that
   the *violating* statement is rejected.
4. **Reconcile on money.** If revenue matches to the penny across every layer,
   the joins, filters and type conversions are right.
5. **Prove the tests fail.** A suite that has never failed is untested.
